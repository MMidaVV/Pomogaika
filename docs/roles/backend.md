# Backend-разработчик

Главная роль с первого коммита. Без этого ядра остальные не на чем стоять.

- Делает одно ядро, не «три чат-бота»: события, политики, брони, каналы, задачи, замок.
- Мультитенантность сразу: у каждой сущности есть собственник и объект.
- Брони без LLM: письмо Авито за секунды, iCal как сверка. Не обещаем календарь «в ту же секунду».
- Политики как код: что можно само, что с подтверждением, что никогда. Отмену брони и возврат система не делает.
- Бот собственника: новая бронь, конфликт с оценкой «что дешевле отменить», кнопки человеку, «закрой 10–12 мая».
- Дальше по срезам: гостевой канал, FSM клинера, адаптер замка. Если у замка нет API — ручной контур, ядро не стопорится.
- Не делает в фазе 1: веб-панель, MAX, биллинг, витрины, автоцены, оплату клинерам.

Короткая сводка всех ролей: [README.md](README.md). Ниже — полный текст, его можно слать кандидату.

## Продукт

Pomogaika — ИИ-диспетчер в Telegram для собственников 1–10 объектов посуточно. Календарь по площадкам, общение с гостями, задачи клинеру, коды замка, отчёт собственнику. Заменяем координатора, не клинера.

Пилот: объект KaVa, Зеленоградск. Авито уже есть, умный замок стоит. Главная метрика: **часы собственника на одну бронь**.

Это **главная инженерная роль** на фазах 0–2. Архитектура: [architecture.md](../architecture.md). План срезов: [PLAN.md](../PLAN.md).

## Когда вы нужны

С первого коммита. Мультитенантность (`owner_id`, `property_id`) не «потом». Без ядра срезы гостя, клинера и замка не на чем стоять.

## Что делаете вы

Ядро, не «набор ботов».

- Домен в Postgres, миграции Alembic, строгие статусы.
- Журнал событий append-only и журнал действий агента: что / почему / кто разрешил. Журнал нельзя править.
- Политики как код: один вход `check(action, context)`. Режим `auto | confirm | never`. LLM не решает, можно ли выдать код или отменить бронь.
- Очередь на старте: таблица outbox + воркер.
- Слой броней **без LLM**: IMAP-парсер писем Авито (быстрый путь), iCal (сверка, дедуп, сводный экспорт без петли). Заезд и выезд в один день — не конфликт. Пересечение — сущность `BookingConflict`, считаем стоимость отмены, решение принимает человек.
- Шлюз каналов: интерфейс `Channel` (пишет первым, окно ответа, identity). Сначала Telegram Bot API и Telegram Business. Логика агента от канала не зависит.
- Один агентный движок, три роли. Инструменты вызываются только через политики.
- FSM задач подрядчика: `created → assigned → accepted → in_progress → done | failed | expired`. Таймеры эскалации.
- Адаптер замка: выдать/отозвать код на интервал, событие открытия. Если облако без API — ручной контур, ядро не блокируется.
- Бот собственника: уведомления, конфликт кнопками, «закрой 10–12 мая», подтверждение черновиков гостю.

Порядок срезов фазы 1: ядро и брони → гость в копайлоте → клинер → замок.

## Чего не делаете вы

- Не ходите в личные аккаунты через MTProto, не пишете юзерботы, не делаете computer use поверх мессенджеров.
- Не обещаете синхронизацию iCal «в ту же секунду».
- Не отменяете брони, не обещаете возвраты и скидки от имени системы.
- Не проводите оплату клинерам и не ведёте их налоги.
- Не ставите цены сами и не публикуете объявления под нашим аккаунтом.
- Не делаете веб-панель, MAX, биллинг и движок цены в фазе 1.
- Не кладёте базу знаний объекта в системный промпт: knowledge — данные.

## Стек

- Python 3.12, FastAPI, SQLAlchemy, Alembic, Postgres
- aiogram 3, Telegram Business (`business_connection_id`)
- Docker Compose, VPS в РФ
- Часовой пояс объекта хранится явно (Калининград UTC+2, площадки часто в МСК)

## Как поймём, что получилось

- Новая бронь из письма за секунды попадает в домен, даты закрываются, собственник получает три строки: кто / когда / сколько.
- Пересечение не «теряется»: есть конфликт, оценка отмены, кнопки человеку.
- Любое действие агента воспроизводится по журналу.
- Тесты без LLM: парсер писем, пересечения дат, политики, FSM задачи, окно выдачи кода (оплата + не раньше 2 часов до заезда).
- На пилоте — ноль овербукингов и падение часов собственника на бронь.
