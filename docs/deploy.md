## Кто может войти

Веб-панели больше нет: `https://pomogaika.vddapp.ru/` отправляет на `/app`, демо-страница
убрана из раздачи (файл сохранён в `src/pomogaika/web/demo/index.html`, но никуда не отдаётся).

Каждый запрос к `/api/*` должен нести заголовок `X-Telegram-Init-Data` — это подписанные
ботом данные, которые Telegram кладёт в мини-приложение при открытии. Сервер проверяет
HMAC-подпись токеном бота, срок жизни (24 часа) и telegram user id: внутрь пускают
только собственника из `.env` (`TELEGRAM_OWNER_USER_ID`), клинера (`TELEGRAM_CLEANER_USER_ID`)
и собственников, записанных в базе. Без подписи — 401, и это видно снаружи:

```bash
curl -s -o /dev/null -w '%{http_code}
' https://pomogaika.vddapp.ru/api/miniapp   # 401
```

Посмотреть, кого пустит:

```bash
cd /opt/pomogaika && PYTHONPATH=src .venv/bin/python -c   "from pomogaika.web import auth; print(sorted(auth.allowed_user_ids()))"
```

Добавить клинера — вписать его telegram user id в `TELEGRAM_CLEANER_USER_ID` в `/opt/pomogaika/.env`
и `systemctl restart pomogaika`.

## Как добавить человека

Собственник делает это сам из бота, ssh не нужен.

1. В боте — команда `/доступ` (или `/access`). Бот покажет список тех, у кого есть доступ,
   и кнопки: «Пригласить» и «Убрать» напротив каждого приглашённого.
2. «Пригласить» — бот пришлёт ссылку вида `https://t.me/kava_pomogaika_bot?start=invite_<код>`.
3. Переслать ссылку человеку. Он нажимает «Запустить» — доступ открыт, собственнику приходит
   уведомление, что приглашение принято.

Ссылка **одноразовая** и живёт **сутки**. Второй раз по ней не войти, просроченную бот отклонит.
Числовой telegram id узнавать не надо.

Что получает приглашённый: полный доступ — мини-приложение, вход в браузере и команды бота.
Ролей нет, это осознанный выбор для пилота; клинер — исключение, он остаётся в своём сценарии
(`bots/cleaner.py`) и пультом собственника не становится.

Убрать доступ — та же команда `/доступ`, кнопка «Убрать». Собственника убрать нельзя:
ни из `.env`, ни из таблицы `owners` — иначе можно запереть самих себя. Браузерная сессия
отвалится сразу: она проверяется на каждый запрос, а не только при входе.

Где это в коде: `src/pomogaika/services/access.py` (приглашения и список),
таблицы `access_users` и `invites`, команда и кнопки — в `src/pomogaika/bots/telegram.py`.

## Вход из браузера

Админу не всегда удобен телефон, поэтому тот же мини-апп открывается в обычном браузере:
https://pomogaika.vddapp.ru/login — кнопка «Log in with Telegram». Человек подтверждает вход
в своём Telegram, сервер проверяет подпись и выдаёт cookie-сессию на 30 дней. Пароля нет,
вход именной, список допущенных — тот же самый.

**Обязательный шаг в BotFather** (без него виджет ругается «Bot domain invalid»):

```
@BotFather → /setdomain → выбрать @kava_pomogaika_bot → отправить: pomogaika.vddapp.ru
```

Как это устроено, если придётся чинить:

| Кусок | Где |
|---|---|
| Проверка подписи виджета | `verify_login_widget` в `src/pomogaika/web/auth.py` |
| Выдача и чтение cookie | `make_session` / `read_session` там же |
| Страница входа | `src/pomogaika/web/static/login.html`, имя бота подставляется на лету |
| Приём ответа виджета | `GET /auth/telegram` в `app.py` |
| Выход | `GET /logout` — чистит cookie |

Cookie подписана токеном бота, лежит `HttpOnly` + `Secure` + `SameSite=Lax`, на сервере
ничего не хранится. Сменить токен бота = разлогинить всех, это же и аварийный рубильник.

Подписи у мини-аппа и у виджета считаются по разным формулам — у мини-аппа ключ
`HMAC(b"WebAppData", token)`, у виджета `SHA256(token)`. Это не опечатка, так у Telegram.

Для локальной разработки проверку можно выключить: `TELEGRAM_AUTH_REQUIRED=false` в локальном `.env`.
На сервере так делать нельзя — ручки выдают коды от двери и данные гостей.

## Занятость, а не «брони»: как читать шахматку

**Одна занятость — одна полоса.** Площадки зеркалят друг друга: бронь пришла на Авито,
Суточно закрыло те же даты и отдало их в своём календаре как «Забронировано». Раньше это
рисовалось двумя полосами и читалось как овербукинг. Теперь склеивается в одну
(`services/stay.py`, `merge`), а по нажатию видно, откуда знаем про эти даты:

```
Откуда знаем про эти даты
Суточно — занято
Авито — даты закрыты
```

**Две настоящие брони не склеиваются никогда.** Склейка срабатывает, только если хотя бы
одна запись безымянная. Две брони с именами на пересекающихся датах — это настоящий
конфликт, и прятать его нельзя (`_can_merge`).

**Закрытия площадки — не брони.** В одном iCal лежат и брони («Avito (Booked)»),
и блокировки дат («Avito (Closed)»). Первые идут в брони, вторые — в закрытые даты
(`is_block_label`, `_upsert_ical_block`). Старые записи разбирает `retire_ical_blocks`.

**Про занятость без имени не бывает тревог.** Календарь площадки отдаёт только даты —
ни оплаты, ни контактов. Требовать по такой записи «отметьте оплату» бессмысленно, поэтому
она показывается как «Даты заняты», а в готовности написано, что имя и сумма придут из письма.
Раньше такие записи давали 26 ложных «требует внимания» из 30.

**Пересечения с закрытыми датами пересматриваются.** Раньше конфликт с блоком создавался
один раз и висел вечно (`if row.block_id: continue`). Теперь: закрытие пришло с площадки,
а занятость безымянная — это одно и то же, конфликта нет; закрыли даты сами, а там бронь —
конфликт настоящий, остаётся.

## Вкладка «Брони»: готовность вместо перечня

Список показывает текущие и ближайшие, завершённые — в «Архиве». Фильтры: текущие,
нужен человек, проживают, архив.

Карточка отвечает на два разных вопроса, и они намеренно разведены:

- **этап проживания** — ожидается, проживает, завершена (`stage`);
- **нужен ли человек** — «Всё по плану» или «Нужно решение» с перечнем причин (`attention`).

Плюс ближайшее событие человеческим языком («Заезд завтра в 15:00»), состояние подготовки
по пунктам (общение, уборка, календари, код доступа) и деньги, когда они известны.
Всё считается в `services/stay.py`: `next_event`, `readiness`, `attention`.

## Почта площадок (IMAP) — подключена 30.09.2026

Ящик `kava7@list.ru` на `imap.mail.ru`. Пароль — для внешних приложений, лежит
в `/opt/pomogaika/.env`. Фоновый цикл проверяет почту раз в `IMAP_POLL_MINUTES` минут.

**Что какая площадка реально даёт в письмах** (проверено на 175 письмах живого ящика):

| Площадка | Что в письме | Разбор |
|---|---|---|
| Яндекс | имя гостя, даты, взрослые и дети, номер брони | `letters.parse_yandex` |
| Островок | имя, даты, номер брони, гостей | `email_parser` (старый) |
| Суточно | номер брони, даты, предоплата + оплата при заселении, число гостей, телефон и имя | `letters.parse_sutochno` |
| Авито | **ничего**: ни имени, ни дат, ни номера — только «Вы сможете получить N ₽» | — |

Суточно шлёт про одну бронь несколько писем — «Новый запрос», «Гость внес предоплату»,
«Гость отказался», — и в каждом есть номер брони. Связывать их вручную не нужно: они
сходятся по номеру сами. Имя гостя приходит только в письме о предоплате (в подписи
у телефона), поэтому у броней без предоплаты его не будет.

Письмо, где чего-то нет, **не затирает** уже известное: пустое имя не сотрёт имя из
предыдущего письма, а нулевое число гостей — прежнее. Это и позволяет собирать бронь
по частям из разных писем.

**Из писем Авито бронь собрать нельзя.** Это не недоработка парсера: деталей в письме
просто нет, Авито отправляет к себе в кабинет. Имя гостя по Авито появится только
через Avito Messenger API или руками.

Письма свёрстаны таблицами — подпись в одной ячейке, значение в следующей, поэтому
разбор построчный (`platforms/letters.py`), а не регулярками по всему тексту. HTML
чистится в `mailbox.strip_html`: без этого в имя гостя однажды приехало `</td>`.

Разовый разбор истории при первом подключении ящика (иначе все письма уже прочитаны
и мы не увидим существующих броней):

```bash
cd /opt/pomogaika && PYTHONPATH=src .venv/bin/python -c "
from pomogaika.db import SessionLocal
from pomogaika.services.mail import poll
s = SessionLocal(); print(poll(s, limit=200, unseen_only=False)); s.commit()
"
```

Два решения, принятых осознанно: читаем **только письма площадок** (`PLATFORM_SENDERS`),
личная переписка не трогается; помечаем прочитанным **только разобранное** — не разобрали,
письмо осталось непрочитанным, ничего не потерялось.

## Когда пересечение — настоящее

Правило одно, и им пользуются и поиск, и проверка (`bookings_conflict` → `find_overlaps`;
раньше они расходились, и конфликты закрывались, а следом создавались заново):

- **две брони с именами** на пересекающихся датах — настоящий овербукинг, требует человека;
- **что угодно с безымянной занятостью** — не конфликт: календари площадок имён не отдают
  и зеркалят занятость друг друга;
- **закрытие, пришедшее из календаря площадки** — не конфликт ни с чем;
- **наше собственное закрытие поверх брони** — конфликт, требует решения.

Овербукинг мы видим по письмам, где есть имена, а не по календарям. На живых данных
это дало один настоящий конфликт (две брони Яндекса 23–28 июля) вместо 46 ложных.

## Ответы гостям: библиотека и формулировки объекта

Раньше ответы жили в одном файле `ops/kava/faq.yaml`, а промпт модели начинался словами
«Ты диспетчер апартаментов KaVa для собственника Галины». Правки админа через бота
сохранялись в базу и до ответов гостям не доезжали — база и файл были разными местами.

Теперь два слоя:

**Библиотека ситуаций** (`services/library.py`, таблица `scenarios`) — общая на все объекты,
ведём мы. Двадцать поводов, по которым пишет гость: заезд, код, парковка, скидка, поломка,
шум. У каждого шаблон с подстановками вида `{parking}` и класс вопроса, от которого зависит
политика. Политики остаются кодом: иначе первый же админ напишет «вернём деньги»
и создаст обязательство от лица собственника.

**Ответы объекта** (`services/answers.py`, таблица `property_answers`) — свой текст поверх
ситуации и свои ситуации, которых в библиотеке нет. Ведёт админ объекта.

Порядок поиска ответа: свой текст объекта → шаблон ситуации с фактами объекта → модель
с фактами того же объекта → человек. **Если факта нет — ситуация не отвечает вовсе**
и уходит человеку: выдумывать парковку, которой мы не знаем, хуже, чем промолчать.

Меню → **«Ответы гостям»**: список ситуаций со статусом (свой ответ / по шаблону /
не хватает фактов), правка текста, добавление своей ситуации, кнопка **«Проверить ответ»** —
вводишь вопрос гостя и видишь, что именно уйдёт, ничего не отправляя.

**Мастер «Об объекте»** — двенадцать вопросов (парковка, Wi-Fi, как заехать, что рядом,
залог, животные…). Заполнил — и шаблоны библиотеки начинают отвечать сами. Это и есть
механизм подключения нового объекта: пятнадцать минут вместо дня ручного написания текстов.

При первом запуске нынешние сорок ответов KaVa разложились по ситуациям библиотеки
и стали её собственными ответами — объект отвечает ровно то же, что отвечал.

## Календари площадок: откуда берутся брони

Брони приходят из iCal-ссылок площадок (Авито, Суточно, Островок, Яндекс). Источник один,
а поводов забрать два:

- кнопка **«Обновить календари»** в мини-приложении (меню → Каналы продаж);
- **сам, раз в 30 минут** — фоновый цикл, `ICAL_SYNC_MINUTES` в `.env`, `0` выключает.

До 29.09.2026 автоматического обновления не было вовсе: календарь показывал то, что забрали
в последний раз руками. Из-за этого настоящая бронь могла неделю не появляться в шахматке,
хотя на площадке она есть.

Что важно понимать про iCal:

- **Брони не удаляются никогда.** В коде нет ни одной операции удаления брони. Если бронь
  пропала из шахматки — она либо отменена (`status=cancelled`, площадка прислала отмену),
  либо это была учебная бронь, снятая автоматически.
- **Учебные брони снимаются сами**, когда в календаре набирается три и больше живых
  iCal-броней: `retire_demo_bookings` в `services/bookings.py`. В журнале это выглядит как
  «Сняла N учебных броней: в календаре уже живой iCal».
- Молчащая площадка не ломает остальные: её ошибка попадает в отчёт, другие забираются.

Посмотреть, что реально лежит в базе за период:

```bash
cd /opt/pomogaika && PYTHONPATH=src .venv/bin/python -c "
from pomogaika.db import SessionLocal
from pomogaika.models import Booking
s = SessionLocal()
for b in s.query(Booking).order_by(Booking.check_in).all():
    print(b.id, b.platform, b.guest_name, b.check_in, b.check_out, b.status, b.source)
"
```

## Закрыть и открыть даты

Закрытые даты («Закрыто у нас» в шахматке) — это наш собственный блок, на площадки он
не уходит. Ставится и снимается двумя способами.

**В мини-приложении.** Шахматка → нажать на серую полосу закрытия → карточка «Закрыто у нас»
→ кнопка **«Открыть эти даты»**. Даты сразу освобождаются.

**Словами боту.** «закрой 28–30 сентября» ставит блок, «открой 28–30 сентября» снимает все
закрытия, попавшие в этот отрезок. Понимает также «сними» и «разблокируй».

Важно различать: если дата занята **бронью**, эти способы её не тронут — бронь снимается
на площадке руками, бот этого не делает намеренно. Открываются только наши собственные блоки.

Снятие блока убирает и пометки пересечений, которые он породил, и пишется в журнал действий
(`open_dates`). Код: `open_dates` и `blocks_in_range` в `services/bookings.py`,
разбор фразы — `parse_open_command` в `domain/dates.py`.

## Итог проживания, МВД, турналог

**Итог проживания.** Карточка брони → «Итог проживания»: отзыв, чек, залог (сколько взяли,
сколько вернули, за что удержали), конфликт (со стороны гостя, заказчика или обеих) с описанием
и урегулированием. Через сутки после выезда бот напоминает один раз на бронь, если итог не закрыт.
Итог считается закрытым, когда отвечено про все четыре пункта.

**Регистрация гостей в МВД.** Меню → «Регистрация гостей в МВД». Показывает окно вокруг сегодня:
ближайшие заезды и последние две недели. По каждой брони — список гостей и статус:
нужно подать → подано → подтверждено.

Страница ничего никуда не подаёт. Прямого канала в МВД у нас нет и быть не может — подача идёт
либо через аккредитованный сервис, либо руками через Госуслуги или МФЦ. Здесь только след:
кто, когда, в каком статусе. **Номера документов и сканы намеренно не хранятся** — это
персональные данные, защищать которые нам сейчас нечем, а для учёта они не нужны.

Кандидат на подключение — **СКАЛА-Гостиница**, её используют многие посуточники.
Чтобы встроить подачу, нужно от неё три вещи: документация на интеграцию (есть ли вообще
programmatic-доступ или только выгрузка файлом), формат обмена и порядок авторизации.
Статусы у нас уже совпадают с логикой подачи: нужно подать → подано → подтверждено,
поэтому встраивание не потребует переделки — добавится только отправка и приём ответа.
Если API нет, а есть выгрузка — сделаем экспорт файла нужного формата прямо с этой страницы.

**Отчёт турналога.** Меню → «Отчёт турналога»: ночи месяца, база и налог, с листанием по месяцам.
Ночь привязана к дате, когда гость лёг спать: ночь с 30 июня на 1 июля — июньская. Сумма брони
делится пропорционально ночам, попавшим в месяц.

Ставка и минимум за сутки — в настройках, по умолчанию 1% и 100 ₽:

```
TOURIST_TAX_PERCENT=1.0
TOURIST_TAX_MIN_RUB_PER_NIGHT=100
```

Применим ли налог к конкретному объекту — вопрос к бухгалтеру, а не к этой странице:
он касается средств размещения из реестра, и правила менялись. Мы даём арифметику и выгрузку.

Код: `services/outcome.py`, `services/registration.py`, `services/tourist_tax.py`,
таблицы `stay_outcomes` и `guest_registrations`, напоминание — в `services/watch.py`.

## Проверка мини-приложения перед выкаткой

`app.html` — один большой файл, и правка в нём однажды снесла пять функций разом
(`shownObjects`, `objectOf`, `statusChip`, `bookingCard`, `matchQuery`): синтаксис остался
валидным, `node --check` молчал, а шахматка исчезла у собственника на экране.

Поэтому перед выкаткой правок в интерфейсе:

```bash
# снять настоящие данные
curl -b "pomogaika_session=<cookie>"   "https://pomogaika.vddapp.ru/api/miniapp?year=2026&month=10" > payload.json

node tools/render_check.js src/pomogaika/web/static/app.html payload.json
```

Скрипт подсовывает минимальный DOM, зовёт `renderGrid`, `renderBook`, `renderDrawer`
и `bookingCard` на этих данных и печатает, падают ли они и сколько нарисовалось:

```
  renderGrid: ок
  шахматка отрисована символов: 5262
  полос в шахматке: 5
  карточек в списке броней: 3
```

Ноль полос при непустых бронях — значит, сломали отрисовку.

## Обновить код

С ноутбука, из корня проекта:

```powershell
.\deploy\upload.ps1
```

Скрипт пакует `src ops tests docs deploy requirements.txt`, распаковывает в `/opt/pomogaika`,
чинит права (windows-tar кладёт файлы как `rw-rw-rw-`), перезапускает сервис и показывает лог.
`.env` и `data/` не трогает.

Если менялся `requirements.txt`:

```bash
/opt/pomogaika/.venv/bin/pip install -r /opt/pomogaika/requirements.txt
systemctl restart pomogaika
```

## Только один бот на токен

`getUpdates` эксклюзивный: пока сервис работает на сервере, локальный `run.ps1` запускать нельзя —
оба получат `TelegramConflictError`, и бот будет отвечать через раз. Локальная разработка — либо
с остановленным сервисом (`systemctl stop pomogaika`), либо с отдельным тестовым токеном в локальном `.env`.

## Диагностика

```bash
systemctl status pomogaika
journalctl -u pomogaika -f                 # лог приложения и бота
journalctl -u pomogaika --since "1 hour ago" | grep -i error
tail -f /var/log/nginx/pomogaika.error.log
curl -s localhost:8001/api/overview | head -c 300      # приложение мимо nginx
```

Бэкап базы перед рискованным:

```bash
cp /opt/pomogaika/data/pomogaika.db /opt/pomogaika/data/pomogaika.db.$(date +%F-%H%M).bak
```

## Что осталось слабым местом

0. **Токен бота светился в журнале.** httpx писал полный URL запросов к Bot API, а токен
   стоит прямо в пути: до 29.09.2026 он лежал в journald открытым текстом (82 записи).
   Логирование приглушено, но **старые записи в журнале остались**. Если считаете риск
   существенным — смените токен в BotFather. Учтите: смена токена разлогинит всех из браузера,
   потому что сессии подписаны им же.

1. **Ролей нет.** Подпись Telegram проверяется, но собственник и клинер внутри равны:
   клинер, если его добавят, сможет дёргать любые ручки, включая выдачу кода от двери.
2. **Бэкапов нет.** База живёт в одном файле на одной виртуалке. Минимум — крон, который
   раз в сутки копирует `.db` и складывает недельную ретенцию.
3. **SFTP на сервере капризничает** — первая запись по новому пути иногда отдаёт ENOENT.
   `scp` в `upload.ps1` работает стабильно; если поймаете ошибку — просто повторите.
4. **Один воркер и SQLite.** Для пилота нормально, для нескольких объектов и
   параллельных диалогов — узкое место.
