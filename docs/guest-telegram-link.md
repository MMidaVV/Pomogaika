# ТЗ: перевод гостя в Telegram и телефон гостя

Для внешнего разработчика. Проект — Pomogaika, ИИ-диспетчер для апартаментов.
Дата: 14.10.2026. Та же версия есть документом для комментариев:
<https://claude.ai/code/artifact/0360387c-cfc5-4188-ac48-4603392a887c>

## 1. Главное решение, из которого всё следует

**Гость пишет собственнице в личку, а отвечает ему бот через Telegram Business —
и гость об этом не знает. В этом ценность продукта. Ломать её нельзя.**

Отсюда следует то, что легко сделать неправильно: ссылка для гостя ведёт
**в личку собственницы**, а не в бота.

У Telegram это два разных диалога, и они не склеиваются:

| | А. Ссылка в бота | **В. Личка собственницы + Business** |
|---|---|---|
| Ссылка | `t.me/<bot>?start=b_<token>` | `t.me/<username>?text=<текст с кодом брони>` |
| Гость видит | имя и аватарку бота | имя и аватарку собственницы |
| Что делает гость | одно нажатие «Начать» | открывает личку с готовым текстом, жмёт «Отправить» |
| Опознание брони | точное, по токену | по коду в тексте первого сообщения |
| Писать первыми потом | можно всегда после «Начать» | пока действует окно после входящего |
| Требования | ничего сверх бота | Telegram Premium и включённый Business Mode |
| Состояние в коде | нужно сделать | **работает** (`business_connection`, `business_message`) |

Вариант А в объём не входит: там гость видит бота вместо человека. Разбор
`?start=b_<token>` стоит сделать только как дешёвый запасной путь — на случай,
если у собственницы отключится Premium и Business-канал умрёт.

Ссылка выглядит так:

```
https://t.me/<username>?text=Здравствуйте%21%20Бронь%20KAVA-7f3a
```

Гость открывает диалог с собственницей, видит её имя, жмёт «Отправить». Всё сразу
сошлось: диалог в нужном месте, бронь опознана по коду в тексте, и появилось
входящее сообщение, после которого бот вправе писать сам.

### Две проверки до начала работы

1. **Работает ли `?text=` на ссылке на личный аккаунт** на iOS, Android и в
   десктоп-клиенте. Для ботов `?start=` документирован твёрдо, для личных
   аккаунтов поведение `?text=` надо проверить руками, а не доверять на слово.
   Не работает — остаётся ссылка без текста плюс опознание через `match_booking`.
2. **Может ли бот писать в business-диалог первым** и сколько живёт окно после
   входящего. От ответа зависит, уйдёт ли код от двери сам за два часа до заезда
   или потребует нажатия собственницы. Если окно закрывается — в `services/codes.py`
   нужен запасной путь: напомнить собственнице в боте и дать кнопку «отправить код».

## 3. Объём работ

### A. Код брони для ссылки

Новая таблица `guest_links` и сервис `services/guest_links.py`. Образец для
копирования — `invites` и `services/access.py`.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `VARCHAR(32)`, PK | Сам код. Должен быть **читаемым**: `KAVA-7f3a` — гость видит его в тексте |
| `booking_id` | FK `bookings.id` | Куда разворачивается |
| `property_id` | FK `properties.id` | Чтобы не искать объект через бронь |
| `created_at` | `DATETIME` | От него считается TTL |
| `expires_at` | `DATETIME` | По умолчанию выезд плюс сутки |
| `used_at` | `DATETIME`, nullable | Когда по нему впервые опознали гостя |
| `guest_user_id` | `INTEGER`, nullable | Кто опознан — для разбора спорных случаев |
| `revoked` | `BOOLEAN`, default 0 | Собственница может отозвать |

Функции:

1. `issue_link(session, booking) -> str` — создать код и вернуть готовую ссылку
   в личку собственницы. Username брать из настроек, не зашивать в код.
2. `resolve_code(session, text, user) -> Booking | None` — найти код в тексте
   сообщения, проверить срок, отзыв, существование брони и статус `cancelled`.
3. `revoke(session, code)` — пометить отозванным.

**Один код — один человек.** Второй `user_id` по тому же коду не привязывается:
иначе пересланная в чат ссылка отдаст код от двери постороннему. А тот же гость,
написавший второй раз, должен спокойно попадать в свою бронь.

### B. Опознание гостя в личке

Порядок действий, когда приходит business-сообщение:

1. Достать текст. Если в нём есть код вида `KAVA-7f3a` — развернуть через `resolve_code`.
2. `bind_guest(...)` с `business_connection_id` из события. Без него ответ уйдёт
   от лица бота, а не собственницы — это и есть главная ошибка, которую нельзя допустить.
3. Кода нет или гость его стёр — `match_booking` по тексту и датам, как сейчас.
   Не опознали — черновик без брони, собственница привязывает кнопкой.
4. Ответ собирает тот же движок. Транспорт — существующий `_send_to_guest`.
5. Собственнице — уведомление, что гость опознан и к какой броне привязан.

**Про коды от двери.** Опознание гостя **не даёт** права на код. Правила выдачи
живут в `services/codes.py` — оплачено и не раньше двух часов до заезда — и остаются
единственным источником правды. Никаких исключений для «он же перешёл по ссылке».

### C. Ссылка в карточке брони

Самая дешёвая и самая полезная часть: собственница копирует ссылку и сама отдаёт
её гостю — в чат площадки, в любой мессенджер, голосом по телефону. Работает без
SMS-агрегатора, без юрлица и без API площадок.

**Ручка.** `POST /api/bookings/{booking_id}/guest-link` → `{"url": "...", "code": "...",
"expires_at": "..."}`. Повторный вызов отдаёт действующую ссылку, а не плодит новые
коды. Отдельно отзыв.

Ручка живёт под `/api/`, значит автоматически закрыта подписью Telegram через
middleware в `web/auth.py` — добавлять ничего не нужно.

**Интерфейс.** В карточке брони кнопка «Ссылка для гостя»: показать ссылку, кнопка
копирования, готовый текст сообщения рядом. Если гость уже привязан — вместо кнопки
показывать «Гость в Telegram с 12.10».

Текст для гостя — с приманкой, а не «перейдите в нашего бота»:

> Код от двери придёт сюда за 2 часа до заезда. Напишите нам здесь, если что-то понадобится.

Формулировка не должна выдавать бота: гость пишет человеку.

**Осторожно с `app.html`.** Интерфейс мини-аппа — один файл
`src/pomogaika/web/static/app.html` на несколько тысяч строк. Правка поиском-заменой
по диапазону однажды снесла пять функций разом, и шахматка исчезла — синтаксис при
этом был валиден, `node --check` молчал. Перед выкаткой правки интерфейса гонять:

```
node tools/render_check.js src/pomogaika/web/static/app.html payload.json
```

`payload.json` собирается из `build_miniapp(session, year=..., month=...)` на засеянной
базе — проверка зовёт настоящую отрисовку, а не синтаксис.

### D. Телефон гостя из писем

Нужен, чтобы собственница могла позвонить или отправить ссылку руками, и как задел
под SMS позже.

**Где телефон есть, а где нет** (проверено 13.10.2026 на 500 последних письмах ящика):

| Площадка | Писем | С телефоном | Что это за номер |
|---|---|---|---|
| Суточно | 38 | 5 | Телефон гостя — только в письме «Гость внес предоплату», в подписи вида «+7 … — Евгения». Остальные совпадения — 8-800 и +7-499 поддержки из рассылок |
| Островок | 32 | 8 | В письме «[ВАЖНО] подтвердите бронирование» есть поле «Телефон», но **один и тот же номер в 7 письмах** — это контакт размещения, а не гостя. Гостевых максимум два |
| Авито | 49 | 0 | В письмах нет ничего, кроме суммы выплаты |
| Яндекс | 21 | 0 | Только номер поддержки +7 (495) |

**В iCal телефона нет ни у одной площадки** — проверено на живых лентах 13.10.2026:
Авито отдаёт 37 событий с полями только `UID`, `DTSTART`, `DTEND`, `SUMMARY`;
у Суточно есть `DESCRIPTION`, но он пустой; лента Яндекса отдаёт 0 событий.
Это не недоработка парсера: iCal — формат обмена занятостью, персональных данных
в нём нет по устройству.

Что сделать:

1. `Booking.guest_phone` — `VARCHAR(20) DEFAULT ''`, плюс строка в `migrate_sqlite()`.
2. В `platforms/letters.py` телефон уже разбирается — довести его до `ingest_booking`.
3. **Список-исключение служебных номеров** в настройках: номера поддержки площадок,
   любой 8-800 и свой собственный номер. Без этого в `guest_phone` приедет телефон
   собственницы из писем Островка.
4. Пустое значение не затирает известное — так же, как сейчас для имени и суммы
   (`guest_name or booking.guest_name`): Суточно присылает по одной брони несколько писем.
5. В карточке брони показать номер ссылкой `tel:`.

## 4. Куда отдавать ссылку

В объём входят только первые две строки — остальное зависит от внешних решений.

| Канал | Состояние | В объёме |
|---|---|---|
| Руками из карточки брони | нужно сделать (раздел C) | да |
| Яндекс — в ответ на сообщение гостя письмом | транспорт готов (`services/outbox.py`), осталось подставить ссылку в текст ответа | да |
| Суточно, Островок — SMS на телефон из письма | нужен агрегатор, ИП или юрлицо, подпись отправителя | нет |
| Авито — в чат после оплаты | нужен Messenger API: приложение в кабинете, профессиональный профиль и тариф | нет |
| Прямая бронь — в письме-подтверждении | прямых броней пока нет | нет |

**До оплаты уводить гостя с площадки нельзя** — это правила площадок. В письмах Авито
у этого аккаунта уже встречались фразы «В чат вернулись ограничения» и «Ограничения
в чате сняты», то есть антифрод Авито с ним уже работал.

**Переход необязателен.** Гость не перешёл — Помогайка отвечает в исходном канале,
код уходит тем же путём, что и сейчас.

## 5. Безопасность и приватность

За ссылкой стоят коды от двери и данные гостей, поэтому пункты ниже — не пожелания.

1. **Никогда не кладём `booking_id` в ссылку.** `?text=Бронь 41813924` означает, что
   любой подставит другой номер и привяжется к чужой брони. Только случайный код.
2. **Код живёт ограниченно** и отзывается. После выезда плюс сутки — недействителен.
3. **Один код — один человек.** Второй `user_id` по тому же коду не привязывается.
4. **Ответ на битый код ничего не рассказывает.** Не «бронь не найдена» и не «ссылка
   истекла 12 июля», а обычный ответ как незнакомому человеку: иначе подбором кодов
   можно выяснять, какие брони существуют.
5. **Коды от двери — по правилам `services/codes.py`**, не по факту перехода. Цифры
   кодов в базу и в журнал не кладутся — только хвост из двух знаков, так сейчас и так
   должно остаться.
6. **Телефон не логируется.** Ни в `log.info`, ни в события, ни в текст ошибки.
   В карточке — да, в журнале — нет.
7. **Ссылка — тоже секрет.** Не печатать её в логи целиком.
8. **152-ФЗ.** Номер получен от площадки. Информационное сообщение по существующей
   брони — исполнение договора и допустимо; приглашение в сервис ближе к рекламе и
   требует согласия. Текстов согласий в проекте нет — это вопрос к владельцу продукта.

## 6. Критерии приёмки

- [ ] Собственница открывает карточку брони, нажимает «Ссылка для гостя», копирует ссылку
- [ ] По ссылке открывается **личка собственницы** с готовым текстом; после «Отправить»
      сообщение приходит как обычное входящее
- [ ] Бот отвечает в этом же диалоге **от лица собственницы** — в карточке гостя нет
      признаков бота
- [ ] Бронь опознана по коду; в брони появились `guest_telegram_user_id`, `guest_chat_id`
      и `business_connection_id`
- [ ] Гость стёр код из текста — опознание идёт через `match_booking`, не опознали —
      черновик без брони и кнопка привязки
- [ ] Повторное сообщение тем же человеком работает, другим аккаунтом по тому же коду — нет
- [ ] Просроченный, отозванный и выдуманный код дают один и тот же нейтральный ответ
- [ ] Опознание не выдаёт код от двери раньше срока и на неоплаченной броне
- [ ] Телефон гостя из письма Суточно показан в карточке; номер поддержки и номер
      собственницы в поле не попадают
- [ ] Все существующие тесты проходят (на 13.10.2026 их 106), плюс новые
- [ ] `node tools/render_check.js` отрисовывает шахматку, список броней, меню и карточку

**Новые тесты** — в `tests/test_core.py`, без сети, на временной базе через `tmp_path`
и `seed_if_empty` (готовые примеры там есть):

1. код разворачивается в нужную бронь и ставит `used_at`;
2. просроченный и отозванный коды не работают;
3. второй `user_id` по тому же коду получает отказ, первый — доступ;
4. повторный вызов ручки не плодит новые коды;
5. business-сообщение с кодом создаёт черновик с `business_connection_id`;
6. телефон из письма Суточно сохраняется, а номер из списка-исключения — нет;
7. пустой телефон в повторном письме не затирает сохранённый.

## 7. Чего делать не надо

Всё ниже обсуждалось и отвергнуто — не из осторожности, а по проверенным причинам.

| Идея | Почему нет |
|---|---|
| Вести гостя в чат с ботом | Гость увидит бота вместо человека и потеряет ощущение живого общения — это ровно та ценность, ради которой всё делается |
| Брать телефон из iCal | Проверено 13.10.2026 на живых лентах: телефонов нет ни у одной площадки |
| Puppeteer и автоматизация кабинета Авито | Антифрод, 2FA, протухание сессии и бан аккаунта собственницы — а вместе с ним объявления, брони и выплаты. Запрещено в `docs/PLAN.md`, `docs/architecture.md`, `docs/product.md` |
| Юзербот Telegram (MTProto) для письма по номеру | То же: прямой запрет в документах проекта и риск для личного аккаунта |
| Рассылать одно и то же в Telegram, MAX и WhatsApp сразу | Ни один из трёх не даёт писать первым по номеру; есть ли у номера эти мессенджеры — неизвестно; три одинаковых сообщения — спам, а WhatsApp ещё и платный за каждое |
| Гостевой веб-чат в сервисе | Нет пушей, нет опознания, нет причины открыть ссылку второй раз. Мини-апп — пульт собственника |
| Переделывать движок ответов или модельный контур | Работает и проверен тестами. Задача — только транспорт до гостя |

## 8. Как поднять проект

Нужен Python 3.11+, Windows или Linux.

```
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
.\run.ps1
```

Тесты: `.\.venv\Scripts\python.exe -m pytest` — должно быть 106 passed.

Что знать до первой правки:

- **Свой тестовый бот обязателен.** `run.ps1` поднимает бота long-polling'ом в том же
  процессе; с одним токеном локально и на сервере одновременно обе стороны получают
  `TelegramConflictError`.
- **Business Mode включается в BotFather**, не в настройках Premium. Ошибка
  `This bot doesn't support secretary mode yet` означает, что он не включён;
  проверка — `can_connect_to_business: true` у бота. Подробности в `docs/telegram.md`.
- **Ручки `/api/*` закрыты подписью Telegram.** Для локальной отладки
  `TELEGRAM_AUTH_REQUIRED=false` в `.env`. На сервере так делать нельзя.
- **Сейчас система рассчитана на один объект:** `session.query(Property).one()` стоит
  примерно в 22 местах. На втором объекте падает с `MultipleResultsFound`. В этой задаче
  чинить не нужно, но и новых таких мест добавлять не стоит — передавайте `property_id`.
- Вебвью Telegram кэширует мини-апп: `/app` и `/login` отдаются с `no-store`, в шапке
